## فصل ۲ — وضعیت صفر (Baseline فنی امروز)

### ۲.۱ — پایگاه داده

- موتور: SQLite (WAL) — `db/custom.db` ~۲۹۳MB · ۵۹ مدل Prisma · ۷۲ هزار رکورد
- دسترسی: Prisma ORM از `src/lib/db.ts` (تک‌نمونه، globalThis-cached)
- بکاپ: `VACUUM INTO` هر ۶ ساعت (نگهداری ۳ نسل) + بستهٔ بقا ۵ نسل
- شناخته‌شده‌ها: Int32 سرریز پریدا (ترمیم PN-018 با نرمال‌ساز + گارد ۵۱ستونی)،
  تاریخ epoch-ms در SQL خام، WAL سالم (سنک همزمان با خواندن ۰٫۰۰۶s)

### ۲.۲ — بار عملیاتی اندازه‌گیری‌شده (شواهد PN-020)

- فهرست M1 (۲۷٬۷xx ردیف): پاسخ ۰٫۱۲–۰٫۱۷s زیر سنک همزمان
- سنک کامل ARM: ~۷۰٫۸s (۱۳۰+ صفحه × ۴۰۰ms rate + غنی‌سازی)
- حلقهٔ مغز: ۶۰ دقیقه · drift-guard: ۶ ساعت · diagnosis: ۶ ساعت
- پیک Build: ۲۱۳۵MB tracing (تیکت سخت‌افزاری D1 باز)

### ۲.۳ — ریسک‌های مقیاس (چرا SQLite کافی نیست)

۱. **نویسندهٔ واحد:** SQLite یک نویسندهٔ هم‌زمان دارد؛ Worker + API + سنک
   صفحه‌ای تازه (PN-022-A) روی هم، صف قفل می‌سازند.
۲. **بدون شبکه:** چند-شهری = چند فرایند/گره؛ فایل مشترک بین گره‌ها ممکن نیست.
۳. **پشتیبان‌گیری آنی:** VACUUM INTO کل فایل را قفل می‌کند؛ pg_dump جدول‌محور است.
۴. **مقیاس افقی آینده:** read-replica و sharding شهرها فقط در PostgreSQL معنا دارد.

## فصل ۳ — مهاجرت PostgreSQL (فقط تست — قید PN-022-A)

### ۳.۱ — راهبرد «تست اول، تولید هرگز بدون گواه»

```
مرحلهٔ A (PN-022-A): اسکیمای سازگار + پایگاه تست مهاجرت‌یافته + بنچمارک
مرحلهٔ B (PN-022-B): دو-نویسی آزمایشی (SQLite منبع حقیقت، PG سایه)
مرحلهٔ C (PN-022-C): سوییچ تولید با حضور مالک + بازگشت اضطراری
```

تولید تا پایان PN-022-C روی SQLite می‌ماند — این سند هیچ سوییچ تولیدی تعریف
نمی‌کند. هر سه مرحله گواه JSON مستقل دارد.

### ۳.۲ — سازگاری اسکیما (۵۹ مدل)

ممنوعه‌های SQLite-محور که باید در اسکیمای دوگانه حل شوند:

| الگوی فعلی | مسئله در PG | راهکار |
|---|---|---|
| `@@index(odelId, checkedAt])` | نام ستون `odelId` (تایپوی تاریخی مدلId) | عین‌نامی حفظ (تغییر نام = تغییر رفتار؛ ثبت DEBT) |
| `Prisma.DbNull` در JSON nullable | رفتار متفاوت PG jsonb | ممیزی کامل فیلدهای Json? (۱۹ فیلد) |
| `DateTime @default(now())` + epoch-ms خام | timezone | همیشه `timestamptz` با mode UTC (تست تاریخ پریدا) |
| `Int` با مقادیر ۱۶ میلیاردی نرمال‌شده | سرریز دوباره | گارد int-overflow روی هر دو موتور (۵-ح) |
| `SqlRaw PRAGMA` (quick_check/integrity) | بدون معادل | لایهٔ `dbHealth()` با شاخهٔ موتور |
| `VACUUM INTO` | بدون معادل | `pg_dump -Fc` در backup-rotation (شاخهٔ موتور) |

**قرارداد:** `prisma/schema.prisma` با provider=postgresql در فایل جدا
(`prisma/schema.postgres.prisma`) نگهداری می‌شود — نه تعویض inline. سازگاری
با `prisma validate` هر دو فایل در CI گواهی می‌شود (گام ۵-ر).

### ۳.۳ — خط لولهٔ مهاجرت داده (ابزار `pg-migrate`)

```
SQLite (custom.db) ──► extract.ts (صفحه‌بندی ۵۰۰تایی، کلید طبیعی) ──►
  NDJSON موقت (download/pn022/pg/migration/) ──► load.ts (COPY binary) ──►
  PostgreSQL تست (db/postgres-test)
گواه: شمارش ۵۹ مدل دوطرفه + نمونه‌گیری ۱۰٪ ردیف برابری بایت‌به‌بایت فیلدهای کلیدی
```

قیدها: (۱) صفر تبدیل نوع ضمنی — هر فیلد با مبدل صریح؛ (۲) ترتیب درج به
پیوندها احترام (فرزند پس از والد)؛ (۳) شکست هر صفحه = توقف با گزارش
جزئی (قید صفر-سکوت)؛ (۴) اجرای مجدد idempotent (upsert بر کلید طبیعی).

### ۳.۴ — بنچمارک (gواه postgres-benchmark.json)

هشت سنجهٔ استاندارد روی هر دو موتور با همان داده:

| سنجه | توضیح | هدف PG (تست) |
|---|---|---|
| فهرست M1 صفحه‌بندی | findMany ۵۰ردیف + count | ≤ ۱.۵× SQLite |
| جستجوی پیشوندی کارشناس | contains + COLLATE | ≤ ۲× (جبران با pg_trgm) |
| تجمیع شش‌دامنه بینش | groupBy شش‌گانه | ≤ ۱.۲× SQLite |
| سنک افزایشی ۱۰۰ردیف | upsertBatch | ≤ ۲× |
| حلقهٔ هفت‌گام پیامد | ۷۷۲ جفت + Brier | ≤ ۱.۵× |
| نوشتن هم‌زمان ۴ نویسنده | Worker+API+سنک+تشخیص | > ۴× (برندهٔ اصلی PG) |
| pg_dump vs VACUUM INTO | زمان پشتیبان کامل | ≤ ۱× (بدون قفل نویسنده) |
| اتصال سرد ۵۰ هم‌زمان | pool sizing | بدون خطا (SQLite: خطا) |

**قضیهٔ صداقت:** اگر PG در سنجهٔ منفردِ تک‌نویسنده بدتر بود، مستند می‌شود —
انتخاب PG برای هم‌زمانی و شبکه است نه تک‌کوئری. عدد خام هر دو چاپ می‌شود.

### ۳.۵ — ریسک و بازگشت

- همهٔ مسیرهای تولید در `DATABASE_URL` گره خورده‌اند — سوییچ = تغییر env،
  نه کد (قید طراحی از P2-04).
- بازگشت اضطراری: env به SQLite + ری‌استارت (≤ ۲ دقیقه) — تمرین‌شده در PN-022-C.
- دادهٔ سنک صفحه‌ای (checkpoint) روی هر دو موتور با همان قرارداد کار می‌کند
  (repo-boundary از فاز ۳ این را ممکن کرد).

## فصل ۴ — Feature Factory (کارخانهٔ کاشی)

### ۴.۱ — مسئله

افزودن هر کاشی امروز = دست‌کاری ۶ نقطه: تعریف کاشی، صفحهٔ lazy، رجیستری
bootstrap، روت API + آینهٔ v1 + مانیفست، ایجنت، تست. PN-017 این را با «قرارداد
کاشی» (defineTile) نصف کرد؛ فاز ۱۲ نیمهٔ مکانیکی را کامل خودکار می‌کند.

### ۴.۲ — قرارداد TileDefinition (موجود، عین‌تاریخ)

هر کاشی: `id · version · title · tagline · description · icon · accent ·
component · settings[] · agent{tileId, insightDomains, capabilities} ·
minRole? · order · container?` — گارد audit-tile-contract (گام ۵-ش) این
قرارداد را روی همهٔ ۱۴ کاشی موجود enforcement می‌کند.

### ۴.۳ — مولد `bun run tile:new --name=<kebab>`

```
scripts/feature-factory/tile-new.ts
  ├── src/core/tiles/tiles/<name>/index.ts        (defineTile + register)
  ├── src/core/tiles/tiles/<name>/<Name>Page.tsx  (lazyPage + TilePageProps)
  ├── src/core/agent/<name>-agent.ts             (BaseAgent + insightDomains)
  ├── src/core/repositories/interfaces/<name>.repository.ts  (قرارداد خالص)
  ├── src/app/api/<domain>/<name>/route.ts        (GET OWNER-safe + آینهٔ v1)
  └── tests/pn022-tile-<name>.test.ts             (قرارداد + مرز نقش + آینه)
```

قیدهای مولد: (۱) قالب‌ها از الگوی `market-index` (کاشی مرجع سالم) مشتق؛ (۲)
بدنه‌های منطق با TODO-fail-loud پر می‌شوند (`throw new Error("TILE_SKELETON")`)
— کاشی تا پیاده‌سازی واقعی در فهرست رجیستری ثبت نمی‌شود (flag
`--register` صریح)؛ (۳) هر تولید در AuditLog با `TILE_GENERATED` مهر
می‌خورد؛ (۴) اجرای مجدد روی نام موجود = خطای صریح (صفر overwrite).

### ۴.۴ — سه گارد تازه (گام‌های ۵-ر/ش/ص)

## فصل ۷ — Offline Mode (طراحی — PN-022-C)

### ۷.۱ — سطح‌بندی

- **L1 (موجود):** PWA نصب‌پذیر + شِل آفلاین (کش سرویس ایستا).
- **L2 (طرح):** خواندن آفلاین — آخرین snapshot هر کاشی در IndexedDB (فهرست‌ها
  فقط-خواندنی + مهر «آفلاین · HH:MM»).
- **L3 (طرح):** نوشتن آفلاین — صف اقدامات محلی (ایجاد مشتری/یادداشت) با
  id محلی + sync یک‌طرفه هنگام بازگشت + حل تعارض «آخرین-برنده با شاهد».
- ممنوعه: نوشتن آفلاین روی دادهٔ ARM (منبع حقیقت بیرونی است).

### ۷.۲ — Conflict Resolution

کلید طبیعی + `updatedAt` + شاهد محلی؛ تعارض واقعی = صف بازبینی مالک
(هرگز ادغام خودکارِ بی‌شاهد). سقف صف: ۵۰۰ آیتم · انقضا: ۷ روز.

## فصل ۹ — تست و پذیرش

### ۹.۱ — تست‌های تازهٔ PN-022-A (هدف ≥۶۰)

- سنک صفحه‌ای: ازسرگیری + تلاش مجدد گذرا + جاروی معوق + ترتیب مهر (۱۲)
- رانش: شکاف همگن + توازن نرخ + پاک‌سازی آرتیفکت + ثبات تعیین‌پذیر (۸)
- تشخیص: بررسی‌های بازکالیبره (DATA-004/006، SEC-002، GOV) + آشتی نقش (۱۰)
- Feature Factory: مولد + قرارداد کاشی + اسکلت fail-loud (۱۴)
- PostgreSQL: اعتبارسنجی اسکیما + گواه مهاجرت + بنچمارک (۱۰)
- قوانین ساختاری: BUILD-DISCIPLINE سه قانون تازه (۶)
- رگرسیون: applyIncrementalSync عین قبل + نقش OWNER از رجیستری (۶)

## فصل ۱۲ — ضمیمهٔ عمیق: سنک صفحه‌ای — مشخصات کامل

### ۱۲.۱ — چرا ۷۰ ثانیه سنک شکننده بود (پیش‌تاریخ)

شاهد F4 (PN-020/گام اول): بالادستی ARM پشت nginx؛ خطای گذرای ۵۰۲/۵۰۴
وسط زنجیره = کشتن کل سنک؛ تلاش بعدی از صفحهٔ ۱ = «تأخیرهای مکرر».
maxRetries=۰ در حلقهٔ صفحه‌بندی حتی یک لرزش را نمی‌بخشید.

### ۱۲.۲ — معماری تثبیت‌شده (کد همین جلسه)

```
fetchAllPages(path, token, maxPages, pageLimit, mapRow, baseQuery, opts)
  opts.checkpointId  → ردیف SyncCheckpoint با id="main-sync:<family>"
  opts.onPage(rows)  → اعمال بلافاصله (مسیر افزایشی؛ پیشروی نجات‌پذیر)

چرخهٔ صفحه:
  fetch(پیش از مهر) → armCall maxRetries=2 (بک‌آف ۸۰۰/۱۶۰۰ms فقط گذرا)
  → اعمال صفحه (onPage) → مهر checkpoint (lastCompletedPage=صفحه)
  → فاصلهٔ ۴۰۰ms → صفحهٔ بعد

ازسرگیری: phase=in-progress + pageSize یکسان + lastCompletedPage>0
  ⇒ startPage = lastCompletedPage + 1 (عین resolveCycleStart کاتالوگ)
  ⇒ بودجهٔ صفحات «هر اجرا» (نه از ابتدای چرخه)
```

### ۱۲.۳ — ترتیب‌های حیاتی (قوانین نانوشته‌شده به نوشته)

۱. **داده پیش از مهر:** صفحه اعمال می‌شود، بعد checkpoint جلو می‌رود —
   قطع برق هرگز حفرهٔ داده نمی‌سازد (عین P6.5-11 بند ب).
۲. **جارو فقط با کلید کامل:** چرخهٔ ازسرگیری‌شده کلیدهای ناقص دارد — جاروی
   سنگ‌قبر تا چرخهٔ کامل تازه بعدی تعویق می‌شود (حذف نادرست = حفره).
۳. **خانوادهٔ قرارداد بی‌checkpoint:** واکشی دومرحله‌ای (لیست+جزئیات) —
   اعمال خانواده‌ای همان‌جا؛ مستند به‌عنوان محدودیت صادقانه.
۴. **غیربحرانی‌ها:** شکست تعاملات/بازدید/عرضه-تقاضا = ادامهٔ سنک + چرخهٔ باز
   در checkpoint (صفحات اعمال‌شده = پیشروی نجات‌پذیر).

### ۱۲.۴ — دروازه‌های صحت (تست‌های مرحلهٔ ۶)

- شکست صفحهٔ N با شبکهٔ قطع → اجرای دوم از صفحهٔ N شروع می‌کند (نه ۱)
- ردیف‌های صفحات ۱..N-1 در DB حاضرند (پیشروی نجات‌پذیر)
- چرخهٔ کامل تازه → جارو اجرا شد؛ چرخهٔ ازسرگیری → جارو تعویق
- maxRetries فقط خطای گذرا می‌بخشد (۴xx هرگز)
- legacy (deleteMany+createMany) بایت‌به‌بایت عین قبل

## فصل ۱۳ — ضمیمهٔ عمیق: شکاف همگن — اثبات ریاضی

### ۱۳.۱ — گزاره

برای مجموعهٔ جفت‌های S با مقادیر مشاهدهٔ گسسته، شکاف همگن لایه‌ای
(مرتب‌سازی بر (observed, hash) + توزیع متناوب) پنجره‌هایی می‌سازد که
اختلاف نرخ وقوع آنها حداکثر |L| mod 2 / |S| است (L = تعداد لایه‌ها).

### ۱۳.۲ — شاهد عددی زنده (۷۷۲ جفت واقعی)

| سنجه | شکاف کهنه (file-order ۷۰/۳۰) | شکاف همگن |
|---|---|---|
| نرخ وقوع خط پایه → اخیر | ۰٫۶۴۳ → ۰٫۱۶۸ | ۰٫۵۰۰۰ → ۰٫۵۰۰۰ |
| رانش مفهوم | **۰٫۴۷۴** (کاذب) | **۰٫۰۰۰** |
| Brier پنجره‌ها | ۰٫۲۴۸۰ → ۰٫۱۷۳۶ | ۰٫۲۲۸۶ → ۰٫۲۲۲۷ |
| رانش عملکرد | ۰٫۰۷۴ | **۰٫۰۰۶** |
| رانش داده | ۰٫۰۲۹ | ۰٫۰۳۱ (< آستانه) |

### ۱۳.۳ — قید صادقانه

شکاف همگن «رانش زمانی» را نمی‌سنجد — برای دادهٔ یک‌روزه ممکن نیست؛ فقط
نویز نمونه‌گیری را حذف می‌کند. رانش زمانی حقیقی از جریان زندهٔ
predictions-live.jsonl می‌آید (مهر PN-018 م۵) — داده‌ای که هنوز جوان است.
افت کوهورتی واقعی ۷٪→۳٪ (کشف G5) بررسی میدانی مالک باقی می‌ماند —
این سند آن را پنهان نمی‌کند.
