### پرسش ۲ — BUILD_ID چگونه تولید/ذخیره/به‌روزرسانی می‌شود؟

عین معماری P6519، سالم و خودکار:

- تولید: `generateBuildId` در `next.config.js` = `<gitSha8>-<yyyymmdd>-<hhmm>` — هیچ اقدام دستی لازم نیست.
- انتشار: `NEXT_PUBLIC_BUILD_ID` در باندل + متاتگ `app-build-id`/`app-git-sha` در HTML + endpoint شاهد `GET /api/version` (بدون لاگین، `no-store`) + `VersionBadge` در فوتر UI + ردیف `AppMeta` در DB.
- **شاهد امروز**: publish → `{"buildId":"3e760f5-20260924-0720","gitSha":"3e760f5","env":"production"}` / dev → `{"buildId":"3e760f5-20260924-0721","gitSha":"3e760f5","env":"development"}` / مسیر preview (:81) → همان `3e760f5`. هر سه = `git rev-parse --short HEAD` = `3e760f5`. ✅

### پرسش ۳ — سابقهٔ کهنگی؛ این چندمین بار است و چرا؟

پنج مورد مستند در `docs/diagnosis-preview-publish-stale.md` (کش FC مسیرمحور sw.js · صف خط لوله · فراموشی Complete · مرگ دامنه‌ها · P6518-بی‌پایه). **مورد ششم (این پرونده) ماهیتاً متفاوت است**: نه کش، نه صف، نه فراموشی، نه مرگ دامنه — زیرا infrastructure شاهد نسخهٔ P6519 دقیقاً کار می‌کند و کهنگی صفر است. ریشه‌یابی در بند «تشخیص ریشه‌ای» زیر.

## تشخیص ریشه‌ای — با شاهد git و DB و کد

### الف) ادعای «تغییرات اخیر در فهرست‌ها و فیلتر» = دستور ۰۲۰ (M1/M2) است

آخرین چیزی که مالک دربارهٔ فهرست‌ها و فیلتر سفارش داده (جلسهٔ پیش از دستور شورا):

- **M1 — کاشی آگهی‌های ملک تبریز**: نظام شش‌حالته (منتشر شده / منقضی شده / معامله شده / رد توسط مدیر / نمایش خصوصی / فایل غیر قابل احیا) شامل بینش + ستون وضعیت + فیلتر چندانتخابی + نشانی با کوی/پلاک + تغییر نام ستون به «مالک»
- **M2 — کاشی درخواست‌های ملک تبریز**: ستون منطقه (فقط متن سادهٔ منطقه) + دو تغییر نام ستون

### ب) این تغییرات هرگز پیاده نشده‌اند — شواهد

1. **git (کل تاریخچه، ۱۸۵ کامیت)**: هیچ کامیت M1/M2 وجود ندارد. آخرین کامیت‌های ویژگی: `459939e` (P6.5-15 — کاشی M3 معاملات) و `e7826a5` (P6519 — زیرساخت شاهد نسخه). پس از P6519 فقط docs/chore (`b8dca64`, `36aaad3`, `57173d8`) و کامیت خودکار `3e760f5`.
2. **diff `459939e..HEAD` فقط ۶ فایل**: همگی زیرساخت P6519 (`api/version`, `layout.tsx`, `VersionBadge`, `build-witness`, `instrumentation`) — **صفر فایل فهرست/فیلتر**.
3. **کد فعلی کاشی آگهی**: فیلتر فقط ۲ فیلد (کد آگهی + نام کارشناس)؛ ستون وضعیت Badge خام بدون طبقه‌بندی؛ هیچ فیلتر چندانتخابی؛ سرستون «مالک ملک» (نه «مالک»)؛ هیچ کارت توزیع وضعیت.
4. **کد فعلی کاشی درخواست**: هیچ ستون منطقه‌ای وجود ندارد؛ فیلتر همان ۲ فیلد قدیمی.
5. **DB زنده (شاهد داده)**: `PropertyRecord.status` یازده مقدار خام دارد که شش حالت دستور M1 دقیقاً شش تای آن‌هاست (منتشر شده ۷۸۲ / منقضی شده ۱۶۰۴ / معامله شده ۲۶۶ / رد شده توسط مدیر ۱۵۶ / اکران خصوصی ۶۹ / فایل غیر قابل احیا ۶۴۷۵) — یعنی **داده برای M1 کامل موجود است**، فقط UI ساخته نشده. برای M2: `RequestRecord.areaNamesJson` فقط ۱ رکورد پر دارد (نگاشت فهرست ARM منطقه را ذخیره نمی‌کند) — باید لایهٔ غنی‌سازی هم توسعه داده شود.
6. **چرخهٔ رویداد**: دستور ۰۲۰ (M1/M2) صادر شد → شورا دستور P6519 را با قید «هیچ BLOCK جدیدی از جمله ادامهٔ M1/M2 شروع نشود» جایگزین کرد → P6519 کامل و بسته شد (سه چرخهٔ سبز + گارد) → **M1/M2 ازسرگیری نشد** → مالک دامنهٔ تازه ثبت کرد، لینک‌ها را باز کرد، تغییرات وعده‌داده‌شده را ندید و طبیعتاً گزارش داد «لینک قدیمی است».
