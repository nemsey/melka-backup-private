## پاسخ قطعی به پرسش ۱ — مکانیزم لینک‌ها: از کجا می‌آیند؟

**این پروژه روی پلتفرم Z.AI (space-z.ai) میزبانی می‌شود — نه Vercel، نه Netlify، نه ngrok.**

### لینک Preview (پیش‌نمایش گفتگو)
- قالب: `https://preview-<bot-id>.space-z.ai/`
- سازوکار: لینک اختصاصی همان گفتگو در UI پلتفرم؛ پس از «finalization موفق» (فراخوانی ابزار Complete) فعال می‌شود.
- مسیر فنی: لبهٔ پلتفرم (ALB) → پورت ۸۱ کانتینر (Caddy) → `localhost:3000`
- محتوای سرو‌شده: **وضعیت زندهٔ کانتینر** — یعنی هر کدی که الان روی پورت ۳۰۰۰ اجرا می‌شود (سرور dev با سوپروایزر خودترمیم `.zscripts/dev.sh`).
- ⚠️ نکتهٔ مستند (سه بار اثبات‌شده در جلسات قبل — DELIVERY-GATE-P2 §50 و P4 §22): نشانی preview از داخل کانتینر قابل حدس/کشف نیست (همهٔ `preview-*` های حدس‌زده‌شده ۴۰۴ می‌شوند)؛ فقط از UI پلتفرم قابل دسترس است.

### لینک Publish (دامنهٔ عمومی مالک)
- قالب: `https://<name>-d.space-z.ai/` (آخرین نمونهٔ ثبت‌شده توسط مالک: `j1xyk7gxxf10-d.space-z.ai` — ثبت از طریق مودال Publish پلتفرم با آیکون مداد)
- سازوکار: **استقرار Snapshot روی Alibaba Function Compute (FC)**:
  1. فراخوانی ابزار **Complete** توسط GLM ⇒ پلتفرم اسنپ‌شات می‌گیرد
  2. `.zscripts/build.sh` روی ریپو اجرا می‌شود: `bun install` + `bun run build` → `.next/standalone` + `.next/static` + `public/` + `db/custom.db` + Python runtime + Caddyfile + `start.sh` → بستهٔ `tar.gz`
  3. بسته روی FC مستقر می‌شود؛ `.zscripts/start.sh` اجرا می‌کند: `NODE_ENV=production bun next-service-dist/server.js` (پورت ۳۰۰۰) + Caddy روی ۸۱
- محتوای سرو‌شده: **Snapshotِ زمانِ publish** — نه لزوماً آخرین کدِ کانتینر

## پاسخ قطعی به پرسش ۲ — سازوکار BUILD_ID جلسات قبل

- **تولید**: BUILD_ID پیش‌فرض Next.js — رشتهٔ تصادفی ۲۱ نویسه‌ای (مثل `Tz-Zc0MM3whIZC2wwJXBS`) که `next build` در `.next/BUILD_ID` می‌نویسد. **نه از git sha، نه timestamp — کاملاً تصادفی و غیرقابل ردیابی به کد.**
- **ذخیره**: فقط فایل `.next/BUILD_ID` (موقتی) + **ثبت دستی در worklog.md** با عبارت «BUILD_ID X آماده Publish».
- **چه کسی به‌روز می‌کند**: GLM هنگام build، به‌صورت دستی-روایتی. **هیچ مصرف‌کننده‌ای ندارد**: نه endpoint یی آن را برمی‌گرداند، نه در UI نمایش داده می‌شود، نه در DB ذخیره می‌شود، نه با git HEAD مقایسه می‌شود.
- **تناقض ساختاری کشف‌شده**: BUILD_ID ثبت‌شده در worklog مربوط به build محلیِ GLM است؛ اما استقرار عمومی BUILD_ID خودش را در زمان publish (اجرای build.sh توسط پلتفرم) می‌سازد. یعنی **حتی در بهترین حالت، BUILD_ID ادعاشده با BUILD_ID مستقرشده یکی نیست** — ادعا بدون شاهد زنده بوده است.
- **وضعیت فعلی لحظهٔ تشخیص**: پوشهٔ `.next` امروز (بوت کانتینر ۰۶:۰۵) توسط سرور dev از نو ساخته شده؛ **هیچ بیلد production و هیچ BUILD_ID وجود ندارد**. `server.log` هم وجود ندارد (سرور standalone محلی خاموش).
