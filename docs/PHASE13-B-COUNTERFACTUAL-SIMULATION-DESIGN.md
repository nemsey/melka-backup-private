## فصل ۱ — فلسفه: از «چه می‌شود اگر کنم» تا «چه می‌شد اگر کرده بودم»

ملکا تا پایان فاز ۱۳-الف دو پرسش را جواب می‌دهد:

- **L1 (انجمن/Association):** «آگهی‌های عکس‌دار چه تفاوتی با بی‌عکس‌ها دارند؟» — همبستگی Pearson بر گراف DAG (۶۳۶ نقطه، ۷ گره، ۱۵ یال).
- **L2 (مداخله/Intervention):** «اگر به یک آگهی عکس اضافه کنم، احتمال معامله‌اش چقدر جابه‌جا می‌شود؟» — `do(hasImage += 1) = +۰٫۲۹۳`.

فاز ۱۳-ب پرسش سوم و عمیق‌ترین سطح سلسله‌مراتب Pearl را پاسخ می‌دهد:

- **L3 (پادواقع/Counterfactual):** «این آگهی **مشخص** — با همین قیمت، همین بازدیدها، همین عکس‌ها — **اگر** قیمتش ۵٪ کمتر بود، احتمال معامله‌اش چه بود؟»

تفاوت L2 و L3 دقیقاً همان تفاوت «میانگین جمعیت» و «فرد مشخص» است. L2 می‌گوید به‌طور *میانگین* هر آگهیِ مشابه +۲۹٪ شانس می‌گیرد؛ اما آگهی ۳۴۸۲۶ که ۴۵ بازدید و ۳ عکس و قیمت ۲٫۱ میلیارد دارد، از میانگین فاصله دارد. L3 با سه‌گامی Pearl این فاصله را پر می‌کند:

1. ** abduction (استنباط):** با دیدن ویژگی‌های مشاهده‌شدهٔ همین آگهی، «نویز فردی» او را از فاصلهٔ پیش‌بینی واقعی استنباط می‌کنیم — یعنی `e = y_observed − ŷ(f_observed)`.
2. **action (اقدام):** در دنیای خیالی، ساختار را جراحی می‌کنیم: `do(price −۵٪)` — معادلهٔ ساختاری قیمت را با مقدار جدید جایگزین می‌کنیم.
3. **prediction (پیش‌بینی):** با همان نویز فردیِ استنباط‌شده (که شناسنامهٔ همین آگهی است)، پیامد را در دنیای خیالی بازمحاسبه می‌کنیم.

نکتهٔ حیاتی: در L3 نویز فردی **ثابت می‌ماند** — این همان چیزی است که آن را از L2 متمایز می‌کند و پاسخ «این آگهی اگر…» را ممکن می‌سازد.

موتور ۱۵ (شبیه‌سازی) روی همین پایه一层 بالا می‌رود: به‌جای یک مداخلهٔ منفرد، **مقایسهٔ چند اقدامِ متعارف** (کاهش قیمت، افزودن عکس، بازنشر، تغییر کارشناس) روی یک زمینهٔ مشخص، با رتبه‌بندی نهایی و جدول مقایسه — همه به‌صورت *پیشنهاد*، هرگز اجرا.

### چرا حالا؟

- گراف DAG از PN-023-A زنده و پایدار است (`CausalEdgeRecord` · ۱۶ یال ذخیره‌شده) — زیرساخت L3 از قبل موجود است.
- مالک در جلسهٔ ۰۳۱ سه پرسش عملی مطرح کرد که بدون L3 بی‌جواب می‌مانند: «اگر قیمت ۵٪ کم شود چه؟»، «کدام اقدام برای این آگهی مؤثرتر است؟»، «قبل از اجرا، نتیجه را ببینم».
- مأموریت PN-024 صراحتاً «تصمیم عمیق» را هدف گرفته است.

### ۲.۲ — صفر تغییر در دیتابیس

فاز ۱۳-ب **هیچ جدول جدیدی نمی‌سازد**. گراف علّی از `CausalEdgeRecord` (ساختهٔ ۱۳-الف) خوانده می‌شود؛ سناریوهای شبیه‌سازی state-less هستند و در هر درخواست از نو محاسبه می‌شوند. این تصمیم عمدی است:

1. قانون ۸ سفارش (افزودنی) در بالاترین سطح رعایت می‌شود — این بار حتی افزودنی هم لازم نیست.
2. شبیه‌سازی ماهیتاً «در حافظه» است؛ ماندگاری آن ارزش معماری ندارد و فقط ریسک ناسازگاری می‌سازد.
3. شواهد (witness JSON) برای تکرارپذیری در `download/pn024/` ذخیره می‌شوند، نه در DB تولید.

<a name="فصل-۳"></a>
## فصل ۳ — موتور ۱۴: پادواقع (قرارداد + Pearl L3)

### ۳.۱ — قرارداد نوع‌ها (TypeScript)

```typescript
/** یک سناریوی پادواقعی: «این واحد مشاهده‌شده، اگر X از a به b می‌رفت…» */
export interface CounterfactualQuery {
  /** شناسهٔ سناریو برای روایت — فارسی */
  scenario: string;
  /** ویژگی مداخله‌شده — باید گره گراف باشد */
  feature: string;
  /** مقدار مشاهده‌شدهٔ واقعی (abduction از این) */
  observedValue: number;
  /** مقدار دنیای خیالی */
  counterfactualValue: number;
  /** شاهد واحد: بقیهٔ ویژگی‌های همین مشاهده + پیامد واقعی */
  evidence: {
    features: Readonly<Record<string, number>>;
    outcome: number;
  };
}

export interface Counterfactual {
  scenario: string;
  /** پیش‌بینی مدل برای دنیای واقعی (sanity: باید نزدیک outcome مشاهده باشد) */
  baseline: number;
  /** پیش‌بینی مدل برای دنیای خیالی */
  counterfactual: number;
  /** اثر پادواقعی = counterfactual − baseline */
  delta: number;
  /** اطمینان: کمینهٔ اطمینان یال‌های مسیر مؤثر × اشباع نمونه */
  confidence: number;
  method: "Pearl-L3";
  /** روایت فارسی — الزامی (قانون روایت موتور توجه) */
  reason: string;
}
```

### ۳.۲ — الگوریتم سه‌گامی (abduction · action · prediction)

با گراف SCM خطی `outcome = Σ βᵢ · Xᵢ` (ضریب‌ها از `CausalEdge`):

1. **Abduction:** `e = evidence.outcome − Σ βᵢ·features[گرهᵢ]` — نویز فردیِ همین مشاهده.
2. **Action:** در کپیِ دنیای خیالی، `feature` را به `counterfactualValue` ست می‌کنیم. توجه: اگر خودِ `feature` روی گره‌های میانی اثر دارد (مسیرهای غیرمستقیم)، مقادیر میانی هم بازمحاسبه می‌شوند — به ترتیب توپولوژیک `featureOrder` گراف.
3. **Prediction:** `y_cf = Σ βᵢ·features′[گرهᵢ] + e` — با همان `e`.

`baseline = Σ βᵢ·features[گرهᵢ] + e` (که برابر `evidence.outcome` می‌شود — sanity درونی) و `delta = y_cf − baseline`.

### ۳.۳ — گیت‌های اعتبار (fail-loud — صفر سکوت)

| گیت | شرط | خطا |
|---|---|---|
| `CF_UNKNOWN_FEATURE` | feature در گراف نباشد | پرتاب |
| `CF_NOT_DAG` | گراف مهر DAG نخورده باشد | پرتاب |
| `CF_EMPTY_GRAPH` | گراف خالی | پرتاب |
| `CF_EVIDENCE_MISMATCH` | feature در evidence.features نباشد | پرتاب |
| `CF_SAME_VALUE` | counterfactualValue == observedValue (سناریوی بی‌اثر) | پرتاب — سناریو باید «مغایر واقع» باشد |

### ۳.۴ — اطمینان (confidence)

`confidence = min(confidence یال‌های روی مسیرهای مؤثر از feature تا outcome)` — اگر feature مستقیم به outcome نرسد، اثر صفر است و اطمینان ۱ (بی‌ابهام: هیچ ادعایی نمی‌کنیم). مقدار خروجی همیشه در `[۰٫۶ ، ۱]` چون کف گراف ۰٫۶ است.

### ۳.۵ — رتبه‌بندی سناریوها

`rank(queries: CounterfactualQuery[]) → Counterfactual[]` — مرتب بر اساس `|delta| × confidence` نزولی. هدف: «اولین چیزی که باید امتحان کنی» بالا بیاید.

### ۳.۶ — نمونهٔ واقعی (که witness باید بازتولید کند)

```
سناریو: «کاهش قیمت ۵٪ برای آگهی با قیمت‌متر ۲۰٬۰۰۰٬۰۰۰»
  feature=pricePerMeter · observed=2.0e7 · counterfactual=1.9e7
  baseline (خروجی مدل با نویز فردی) ≈ 0.42
  counterfactual ≈ 0.47  →  delta = +0.05
```

## فصل ۴ — موتور ۱۵: شبیه‌سازی (قرارداد + سه مدل)

### ۴.۱ — فلسفهٔ سه‌مدلی سفارش

سفارش PN-024 سه جزو برای شبیه‌سازی تعیین کرده: **مدل داده + مدل واکنش + مدل بازار**. این سه مدل به ترتیب «چیزی که هست»، «چگونه ملک به تغییر واکنش می‌دهد» و «چگونه بازار پاسخ می‌دهد» را مدل می‌کنند.

### ۴.۲ — قرارداد نوع‌ها

```typescript
/** اقدام پیشنهادی — هرگز اجرا نمی‌شود (قانون ۱۱ سفارش) */
export interface SimAction {
  kind: "PRICE_CUT" | "ADD_IMAGE" | "REPOST" | "AGENT_CHANGE";
  /** پارامتر اقدام: درصد کاهش قیمت، تعداد عکس، … */
  magnitude: number;
  label: string; // فارسی
}

/** زمینهٔ شبیه‌سازی — وضعیت فعلی واحد و بازار */
export interface SimContext {
  currentProbability: number;   // از گراف علّی
  pricePerMeter: number;
  imageCount: number;
  viewCount: number;
  /** فشار بازار: نسبت عرضه/تقاضا — ۱ = متعادل */
  marketPressure: number;
}

export interface SimulationResult {
  action: SimAction;
  /** احتمال معامله در دنیای شبیه‌سازی‌شده */
  simulatedProbability: number;
  /** Δ نسبت به وضع فعلی */
  delta: number;
  /** ریسک‌های مستند این اقدام */
  risks: string[];
  confidence: number;
  /** همیشه false — قفل auto_execute */
  autoExecute: false;
  reason: string; // فارسی
}

export interface ComparisonTable {
  baseline: SimContext;
  results: SimulationResult[]; // مرتب بر اساس delta نزولی
  best: SimulationResult | null;
  recommendation: string; // فارسی
}
```

### ۴.۳ — مدل داده (از گراف علّی)

`simulate` ابتدا `currentProbability` را با `CounterfactualEngine` در نقطهٔ صفر (بدون تغییر) محاسبه می‌کند — یعنی مدل دادهٔ ما همان SCM گراف است؛ هیچ مدل موازی ساخته نمی‌شود (اصل تک‌منبعی حقیقت).

### ۴.۴ — مدل واکنش (نگاشت اقدام → مداخله)

هر `SimAction` به یک `CounterfactualQuery` ترجمه می‌شود:

| اقدام | مداخله | نکته |
|---|---|---|
| `PRICE_CUT(٪)` | `pricePerMeter → pricePerMeter×(۱−pct/۱۰۰)` | ریسک مستند: «کاهش قیمت perceived-value را هم می‌کشد» |
| `ADD_IMAGE(n)` | `hasImage → 1` (اگر ۰ بود) | اثر غیرخطی نرم: فقط انتقال ۰→۱ حساب می‌شود |
| `REPOST` | `viewCount → max(views, median)` | proxy: بازآفرین تازگی |
| `AGENT_CHANGE` | — | بدون یال علّی در گراف فعلی → delta=۰ با reason صادقانه |

اگر یال علّی برای مداخله نباشد، موتور ادعا نمی‌کند — `delta=۰` با دلیل «این گراف هنوز مسیر علّی برای این اقدام ندارد».

### ۴.۵ — مدل بازار (فشار عرضه/تقاضا)

`marketPressure = supply / max(1, demand)` از دو شمارش سادهٔ `PropertyRecord` (عرضه فعال) و `RequestRecord` (تقاضای باز) در سرویس محاسبه و به‌عنوان ضریب تعدیل *خنثی‌کننده* اعمال می‌شود: در بازار اشباع (pressure>1) اثر اقدام‌ها با `1/√pressure` تعدیل می‌شود و در بازار گرم (pressure<1) با `√(1/pressure)` تقویت. این تعدیل **روی delta** اعمال می‌شود نه روی baseline — مدل داده دست‌نخورده می‌ماند. سقف تعدیل ۱٫۵ برابر است (پرهیز از حساسیت شدید).

### ۴.۶ — قفل auto_execute (قانون ۱۱ سفارش — ابدی)

- نوع `autoExecute` در قرارداد `false` literal است (`autoExecute: false` در TypeScript) — هر تلاش برای true خطای نوع می‌دهد.
- `SimulationResult` هیچ شناسهٔ DB و هیچ فراخوانی اثرگذار ندارد — از نظر نوعی «فقط خواندنی» است.
- گارد `audit-counterfactual-purity` حضور `db`/`fetch`/`autoExecute: true` را در هر دو موتور می‌گیرد.

### ۴.۷ — compare

`compare(actions: SimAction[], ctx: SimContext) → ComparisonTable` — هر اقدام simulate می‌شود، مرتب، بهترین انتخاب و توصیهٔ فارسی تولید می‌شود. توصیه همیشه یک قید اخلاقی دارد: «شبیه‌سازی پیشنهاد می‌دهد، تصمیم با مالک/شوراست.»

## فصل ۵ — محیط شبیه‌سازی: سناریوهای استاندارد روی دادهٔ واقعی

### ۵.۱ — چرا سناریوی استاندارد؟

برای مقایسهٔ مکان‌ها و زمان‌ها، چهار سناریوی ثابت تعریف می‌شود که witness و UI هر دو از آن‌ها استفاده می‌کنند:

1. `PRICE_5` — کاهش ۵٪ قیمت (عین مثال جلسهٔ ۰۳۱ مالک)
2. `PRICE_10` — کاهش ۱۰٪
3. `IMAGE_1` — افزودن نخستین عکس
4. `REPOST` — بازنشر (بازدید به میانهٔ بازار)

### ۵.۲ — واحد مشاهده (evidence)

از میانگین ویژگی‌های معامله‌های واقعی (۷۶۸ معاملهٔ غنی‌شده) به‌عنوان «مشاهدهٔ معیار» استفاده می‌شود + یک آگهی واقعی برتر توجه (از موتور ۱۲) به‌عنوان «مشاهدهٔ زنده». هر دو در witness گزارش می‌شوند.

### ۵.۳ — قطعیت و تکرارپذیری

- همهٔ ورودی‌ها عددی و بسته‌بندی‌شده در `SimContext`/`CounterfactualQuery` هستند.
- `now` تزریقی است (عین موتور توجه) — اگر زمانی به تازگی وابسته شود.
- هیچ تولید اعداد تصادفی وجود ندارد — شبیه‌سازی خوش‌تعریف و deterministic است.

### ۵.۴ — مرزهای دامنه و قرارداد مقیاس (تصمیم مهندسی حین پیاده‌سازی — مستند)

**قرارداد مقیاس:** ضرایب گراف ۱۳-الف همبستگی (استاندارد) هستند؛ بنابراین ویژگی‌های **پیوسته به‌صورت z-score** و **باینری به‌صورت ۰/۱** به موتورها داده می‌شوند (سرویس فرا-ذهن با μ/σ نمونهٔ واقعی استانداردسازی می‌کند). این مقیاس با تفسیر PN-023-A سازگار است: `do(hasImage += ۱) = +۰٫۲۹۳`. نتیجهٔ زندهٔ قابل‌باور: کاهش ۵٪ قیمت ≈ ‏+۰٫۹ امتیاز احتمال · ۱۰٪ ≈ ‏+۱٫۹ امتیاز (شاهد ۱۶۵ معامله).

| مرز | قاعده |
|---|---|
| ویژگی‌های باینری | clamp به [۰،۱] |
| ویژگی‌های پیوسته (z) | بدون clamp خاموش — خروجی نهایی قضاوت می‌کند |
| probability خروجی | clamp به [۰٫۰۱ ، ۰٫۹۹] (هیچ‌وقت قطعیت مطلق ادعا نمی‌شود) |
| مداخلهٔ درصدی قیمت | مبدل درصد→z: ‏Δz = ‏−pct × μ/(۱۰۰σ) — سرویس می‌دهد |

**انتشار درونی باحراست از پسماند:** هر گرهٔ میانی در دنیای خیالی `f′ = f_obs + ΔS(والدها)` — پسماند فردی همهٔ گره‌ها (نه فقط outcome) بین دو دنیا ثابت می‌ماند = جوهرهٔ L3 (بازنویسی خاموش نمی‌شود).

<a name="پیوست-پ"></a>
## پیوست پ — شبه‌کد کامل موتور ۱۴ (مرجع پیاده‌سازی)

```text
تابع query(graph, q):
  # گیت‌ها (به ترتیب — صفر سکوت)
  اگر graph خالی            ⇒ پرتاب CF_EMPTY_GRAPH
  اگر graph.dagVerified≠true ⇒ پرتاب CF_NOT_DAG
  اگر q.feature ∉ graph.nodes ⇒ پرتاب CF_UNKNOWN_FEATURE
  اگر q.feature ∉ q.evidence.features ⇒ پرتاب CF_EVIDENCE_MISMATCH
  اگر q.counterfactualValue == q.observedValue ⇒ پرتاب CF_SAME_VALUE

  # ۱) abduction — نویز فردی
  y_hat = Σ (برای هر یال e که e.to==outcome)
          e.coefficient × clamp(evidence.features[e.from] به دامنه)
  e_individual = evidence.outcome − y_hat

  # ۲) action — دنیای خیالی
  features_cf = کپی(evidence.features)
  features_cf[q.feature] = clamp(q.counterfactualValue به دامنه)

  # ۲-ب) انتشار درونی: اگر feature والدِ گره‌های میانی است،
  #        به ترتیب توپولوژیک featureOrder مقادیر میانی بازمحاسبه می‌شود
  برای هر گره n به ترتیب featureOrder:
      اگر n==outcome یا n==q.feature ⇒ ردش کن
      parents = یال‌هایی که to==n
      اگر parents خالی ⇒ ردش کن (برگِ مشاهده — دست‌نخورده)
      features_cf[n] = Σ p.coefficient × features_cf[p.from]   # انتشار خطی

  # ۳) prediction
  y_cf_hat = Σ (یال‌ها به outcome) coefficient × features_cf[from]
  y_cf     = y_cf_hat + e_individual
  baseline = evidence.outcome            # برابر Σ واقعی + e — sanity

  # اطمینان — کمینهٔ یال‌های مؤثر روی مسیر feature→outcome
  activeEdges = یال‌هایی که روی مسیر DAG از q.feature تا outcome‌اند
  confidence = activeEdges خالی؟ ۱ : min(e.confidence برای e در activeEdges)

  # خروجی
  بازگردان Counterfactual {
    scenario: q.scenario, baseline, counterfactual: clamp01(y_cf),
    delta: clamp01(y_cf) − baseline, confidence, method: "Pearl-L3",
    reason: «سناریو X: با نویز فردی {e:.2f}، تغییر {feature} از {obs} به {cf}
            پیامد را از {baseline:.2f} به {y_cf:.2f} جابه‌جا می‌کند (Δ={delta:+.3f})
            با اطمینان {confidence:.2f} از {n} یال مؤثر.»
  }
```

**نکته‌های پیاده‌سازی:**

1. `clamp01` خروجی در `[۰٫۰۱ , ۰٫۹۹]` — چون outcome این گراف «احتمال معامله» است و قطعیت مطلق ادعا نمی‌شود.
2. `e_individual` می‌تواند منفی یا بزرگ باشد (مدل ناقص) — این صداقت مدل است و در reason دیده می‌شود؛ سقف |e| نداریم چون حذفش یعنی انکار فاصلهٔ واقعی.
3. ترتیب توپولوژیک از `graph.featureOrder` موجود (PN-023-A) می‌آید — بازتولید Kahn لازم نیست.
4. `rank` بعد از محاسبهٔ همه، مرتب می‌کند — هیچ حافظه‌ای بین queryها نیست (state-less).

## پیوست ت — شبه‌کد کامل موتور ۱۵

```text
تابع simulate(action, ctx):
  # نگاشت اقدام → مداخله (مدل واکنش)
  انتخاب action.kind:
    PRICE_CUT:
      از = ctx.pricePerMeter
      به = از × (۱ − action.magnitude/۱۰۰)
      ریسک‌ها = [«کاهش قیمت، ادراک ارزش را هم کاهش می‌دهد»,
                «اگر زیر نرخ منطقه برود سیگنال فوریت فروش می‌دهد»]
    ADD_IMAGE:
      اگر ctx.imageCount>0 ⇒ delta=۰ + reason «عکس هست؛ اثر ۰→۱ است»
      از=۰ · به=۱ · ریسک=[«عکس بی‌کیفیت اثر معکوس دارد»]
    REPOST:
      از=ctx.viewCount · به=max(میانهٔ بازار, ctx.viewCount) · ریسک=[«تکرار بدون بهبود، اعتماد را می‌فرساید»]
    AGENT_CHANGE:
      بازگردان delta=۰ + reason «گراف فعلی مسیر علّی برای کارشناس ندارد — بدون ادعا»

  # شبیه‌سازی از طریق L3
  cf = CounterfactualEngine.query(graph, {feature, از, به, evidence از ctx})

  # مدل بازار — تعدیل delta (نه baseline)
  pressure = ctx.marketPressure
  تعدیل = pressure>1 ? 1/√pressure : √(1/pressure)     # سقف [۱/۱٫۵ , ۱٫۵]
  delta_adj = delta × clamp(تعدیل, ۱/۱٫۵, ۱٫۵)

  بازگردان SimulationResult { action, simulatedProbability: baseline+delta_adj,
    delta: delta_adj, risks, confidence: cf.confidence,
    autoExecute: false, reason }

تابع compare(actions, ctx):
  results = [simulate(a, ctx) برای هر a]
  مرتب results نزولی بر delta
  best = results[0] اگر delta>0 وگرنه null
  recommendation = best ? «اقدام پیشنهادی اول: {label} (Δ={delta:+.۳}) — تصمیم با مالک.»
                        : «هیچ اقدامی در این گراف اثر مثبت مستند ندارد.»
```

## پیوست ح — طراحی J1 (پارک اتمی — ریشه ENOSPC)

**زنجیرهٔ مرگ (شاهد درس ۹):** `park-deliver` ⇒ حذف deliver-store ⇒ `prod-watchdog` می‌بیند standalone نیست ⇒ rebuild خودکار ⇒ file-tracing ۲٫۲GB ⇒ ENOSPC.

**راه‌حل سه‌لایهٔ مصوب:**

1. **قفل rebuild:** `prod-watchdog` قبل از هر rebuild چک می‌کند: `PARK_ACTIVE` یا `CI_RUNNING` در `upload/.runtime/` هست؟ ⇒ صبر ۳۰ دقیقه (نه rebuild).
2. **پارک اتمی:** `park-deliver park` اول flag می‌گذارد بعد منتقل می‌کند؛ `restore` اول برمی‌گرداند بعد flag را برمی‌دارد — هر crash وسط کار، flag را باقی می‌گذارد = محافظه‌کار (fail-safe).
3. **درس مستند:** BUILD-DISCIPLINE بند ۱۰ «پارک اتمی» — ترتیب کار: flag → park → build → restore → unflag.

دریل منفی (گواه باید نشان دهد): گذاشتن PARK_ACTIVE دستی ⇒ اجرای watchdog ⇒ گزارش «صبر — پارک فعال» بدون rebuild.
