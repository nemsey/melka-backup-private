# سند طراحی فاز ۱۰ — خودآگاهی (Self-Diagnosis)
**ملکا — PN-020 · ملکا-شورا-ن۰۲۴-۱۴۰۵ · مصوب مالک: «سیستم خودش را می‌شناسد و می‌سنجد»**

---

## ۱. مأموریت و مرز

### ۱.۱ مأموریت
سامانه هر ۶ ساعت یک بار خودش را با ۲۵ بررسی در پنج دسته می‌سنجد، نمرهٔ سلامت ۰-۱۰۰
محاسبه می‌کند، هشدارهای انحراف را در `AuditLog` ثبت می‌کند و گزارش کامل را در جدول
پایای `DiagnosticReport` نگه می‌دارد. خروجی این فاز، ورودی فاز ۱۱ (خودترمیمی) است:
هر بررسیِ ناموفق می‌تواند پیشنهاد ترمیم تولید کند — اما هرگز خودش ترمیم نمی‌کند.

### ۱.۲ مرزهای سخت (قیدهای شورا)
| # | قید | علت |
|---|-----|-----|
| Q1 | صفر تغییر دادهٔ تولید در تشخیص | تشخیص فقط می‌خواند؛ نوشتن یعنی ترمیم (فاز ۱۱ با تأیید) |
| Q2 | صفر اجرای کنش خارجی | هیچ API بیرونی (ARM/PM/دیوار) صدا نمی‌شود |
| Q3 | هر بررسی مستقل و fail-open | شکست یک بررسی چرخه را نمی‌شکند؛ نمرهٔ همان بررسی صفر می‌شود |
| Q4 | هر گزارش ۹۰ روز نگه‌داری می‌شود | عین قاعدهٔ حاکمیت GOV-DECISION — دکترین دادهٔ مقدس |
| Q5 | نمرهٔ سلامت موزون است نه ساده | بررسی بحرانی (مثلاً از دست رفتن DB) سهم بیشتری دارد |

### ۱.۳ جایگاه در معماری مغز
```
پیش‌بینی (فاز ۵) → یادگیری (فاز ۷) → تصمیم (فاز ۸) → حاکمیت (فاز ۹)
                                                      ↓
                          خودآگاهی (فاز ۱۰ — همین سند) ← می‌سنجد
                                                      ↓
                          خودترمیمی (فاز ۱۱ — با تأیید شورا) ← ترمیم می‌کند
```
شورا (جلسهٔ ۰۲۴): «خودآگاهی بدون خودترمیمی ناقص است، ولی خودترمیمی بدون خودآگاهی
خطرناک است.» — فاز ۱۰ پیش‌نیاز منطقی فاز ۱۱ است.

## ۲. قرارداد داده‌ای

### ۲.۱ جدول `DiagnosticReport` (پایا)
| فیلد | نوع | شرح |
|------|-----|-----|
| id | String cuid | شناسهٔ گزارش |
| healthScore | Int | نمرهٔ کلی ۰-۱۰۰ |
| passedCount | Int | تعداد بررسی پاس‌شده از ۲۵ |
| alertsJson | String | آرایهٔ `[{checkId, severity, message}]` — هشدارهای فعال |
| checksJson | String | آرایهٔ ۲۵تایی نتیجهٔ بررسی‌ها |
| triggerSource | String | `worker \| manual` |
| durationMs | Int | مدت چرخه |
| createdAt | DateTime | مهر زمان |

### ۲.۲ قرارداد نتیجهٔ هر بررسی (`DiagnosticCheckResult`)
```ts
interface DiagnosticCheckResult {
  checkId: string;          // شناسهٔ پایدار (DIAG-DATA-001 …)
  category: "data" | "model" | "engine" | "security" | "governance";
  title: string;           // عنوان فارسی
  passed: boolean;          // نتیجه
  weight: number;           // وزن نمره (بندی §۵)
  score: number;            // 0..100 سهم این بررسی
  value: string | null;     // مقدار مشاهده‌شده (خلاصهٔ کوتاه)
  expected: string;         // معیار قبولی
  message: string;          // توضیح فارسی نتیجه
}
```

### ۲.۳ هشدار (`DiagnosticAlert`)
```ts
interface DiagnosticAlert {
  checkId: string;
  severity: "critical" | "warning";
  message: string;         // عین پیام بررسیِ ناموفق
}
```

## ۴. نمرهٔ سلامت (موزون)

### ۴.۱ وزن‌ها
| دسته | وزن مجموع | منطق |
|------|-----------|------|
| داده | ۳۰٪ | بدون داده، همه‌چیز بی‌معناست |
| مدل | ۲۵٪ | مغز پیش‌بینی |
| موتور | ۲۰٪ | زیرساخت اجرا |
| امنیت | ۱۵٪ | مرزهای نفوذ |
| حاکمیت | ۱۰٪ | چارچوب قانون |

### ۴.۲ فرمول
```
healthScore = Σ (check.score × check.weight)     // score هر بررسی ۰ یا ۱۰۰ است
            = ۱۰۰ × Σ(گذرنده × وزن) / Σ(وزن همه)
```
- بررسی پاس = score ۱۰۰ · ناموفق = ۰ (دودویی — ساده، بازرسی‌پذیر، بدون خاکستریِ ساختگی)
- اگر «داده» بحرانی شکست بخورد (DIAG-DATA-001) — نمرهٔ کلی در گزارش هشدار
  critical می‌گیرد؛ خودِ نمره همچنان وزنی می‌ماند (شفافیت کامل).

### ۴.۳ آستانه‌های تفسیر (فقط گزارش — کنش در فاز ۱۱)
| بازهٔ نمره | وضعیت |
|-----------|--------|
| ۹۰-۱۰۰ | سبز — سالم |
| ۷۵-۸۹ | زرد — نیازمند پایش |
| ۵۰-۷۴ | نارنجی — نیازمند پیشنهاد ترمیم (ورودی فاز ۱۱) |
| < ۵۰ | قرمز — هشدار فوری مالک (INFRA_ALERT) |

## ۵. زمان‌بندی و اجرا

### ۵.۱ کار Worker چهاردهم: `diagnosis-cycle`
- فاصله: هر ۶ ساعت (env `MELK_DIAGNOSIS_INTERVAL_H` — پیش‌فرض ۶)
- نخستین اجرا: ۴ دقیقه پس از بوت
- کلید خاموشی: `MELK_DIAGNOSIS=disabled`
- هر اجرا: `runDiagnosisCycle()` → ثبت DiagnosticReport + هشدارهای AuditLog

### ۵.۲ اجرای دستی (OWNER)
- روت `POST /api/admin/diagnosis` (OWNER-only) → اجرای فوری + پاسخ گزارش
- روت `GET /api/admin/diagnosis` → آخرین گزارش + میانگین ۷ اجرای اخیر
- آینهٔ v1 هر دو (تک‌منبع حقیقت)

### ۵.۳ بودجهٔ زمانی
هر بررسی ≤ ۲ ثانیه؛ چرخهٔ کامل ≤ ۱۵ ثانیه (سقف ایمنی ۳۰ ثانیه). بررسی‌های سنگین
(مانند تناقض جداول) با نمونه‌گیری محدود می‌شوند.

## ۶. رابط با فاز ۱۱ (خودترمیمی)

خروجی استاندارد چرخه:
```ts
interface DiagnosisCycleResult {
  reportId: string;
  healthScore: number;
  passedCount: number;      // از ۲۵
  alerts: DiagnosticAlert[];
  // فاز ۱۱ — پیشنهادهای ترمیم از بررسی‌های ناموفقِ قابل‌ترمیم (نگاشت §۷ فاز ۱۱)
  repairCandidates: { checkId: string; suggestedAction: RepairActionType }[];
}
```
- فقط بررسی‌های دارای نگاشت ترمیم (۱۲ از ۲۵ — بند §۷ سند فاز ۱۱) کاندید می‌شوند.
- پیشنهاد ساختن ≠ پیشنهاد اجرا: ApprovalGate فاز ۱۱ صدرِ همه است.

## ۷. پایداری و بازیابی

| سناریو | رفتار |
|--------|-------|
| شکست یک بررسی در میانهٔ چرخه | نمرهٔ همان بررسی صفر + ادامه (Q3) |
| شکست کل چرخه (استثنا) | ثبت نشدن گزارش؛ چرخهٔ بعد دوباره تلاش (شکست = لاگ نه کرش) |
| خالی بودن جدول (بوت تازه) | چرخهٔ اول گزارش اولیه می‌سازد — هیچ فرضی ساخته نمی‌شود |
| پرشدن جدول | نگه‌داری ۹۰ روزه (جاروب نرم در هر چرخه — حذف فقط رکوردهای خودِ تشخیص) |

## ۸. تست‌پذیری (خلاصه — جزئیات در فایل تست)

۳. آستانه‌های تفسیر: مرزهای ۵۰/۷۵/۹۰

۵. مرز ۴۰۱/۴۰۳ روت‌های OWNER
۶. ثبت DiagnosticReport پایا + alerts در AuditLog
۷. دریل منفی: بررسی بحرانی شکست‌خورده → هشدار critical + کاهش نمره
