> **مرجع:** `docs/ARM-PM-RECONNAISSANCE.md` §۱۵-ب (طرح مصوب) · گزارش P6.5-04 §۵ (جدول تخمین) · قواعد محرمانگی §۱.۱۲ سند طراحی PHASE 6.5 (درجه ۱)
> **اجرای فنی:** `scripts/recon-night1.ts` (تنها ابزار مجاز اجرا — گاردها در کد، نه در حافظهٔ انسانی)
> **پنجرهٔ مجاز:** ۲۲:۰۰–۰۶:۰۰ تهران (توقف سخت ۰۶:۰۰) · **سقف کل:** ۱۹۰ GET (توقف خودکار) · **سقف هر Endpoint:** ۲۰۰ GET · **کف فاصله:** ۱۵۰۰ms بین هر دو درخواست

> **🔔 ابلاغیهٔ اجرای فوری — دستور مالک «ملکا-فوری-۰۰۱» (دریافت ۱۴۰۵/۰۶/۲۸ ~۰۶:۵۰ تهران):**
> ۱) قاعدهٔ ۳ (پنجرهٔ زمانی §۱.۱۲) با اختیار صریح مالک برای این اجرا معلق شد — شاهد: رکورد `{event:"window-override", reason:"owner-order"}` در `recon-night1.jsonl` (بند ۲ دستور).
> ۲) چراغ سبز قاعدهٔ ۱۰ (OTP) = خود این دستور (بند ۳). ۳) دامنه: گام‌های ۱ تا ۸ — ۲۵ GET · کف ۱۵۰۰ms · سقف ۱۹۰ (بند ۴).
> ۴) مالک با گوشی در دست (حداکثر ۲ پیامک — بند ۵). ۵) ریسک کندی/flag ساعت پیک: از سوی مالک پذیرفته شده (بند ۶).
> ۶) اجرا: `--force-window` (بند ۷). ۷) گزارش صبحگاهی: JSON log + مقایسهٔ ⏳→✅ (بند ۸).
>
> گام ۹ (teardown در `finally`) گاردِ همیشه‌اجرا است و مشمول دامنهٔ عددی دستور نمی‌شود — در هر حالت اجرا می‌شود. سایر گاردها (سقف‌ها، فاصله، ۴۲۹، ABORT، timeout، صفر payload) دست‌نخورده می‌مانند. کل تماس‌ها: ۲۶ GET (۲۵ داده + ۱ احراز هویت فاز A) + ۳ POST احراز هویت ≪ سقف ۱۹۰.

## ۰. قواعد حاکم (غیرقابل مذاکره — عین §۱۵-ب و §۱.۱۲)

| # | قاعده | پیاده‌سازی در اسکریپت |
|---|---|---|
| ۱ | پنجرهٔ شبانهٔ ۲۲:۰۰–۰۶:۰۰ تهران | گارد `inWindow()` پیش از **هر** درخواست (ساعت تهران از `Intl` با `timeZone: Asia/Tehran` — نه ساعت سرور UTC) |
| ۲ | سقف ۱۹۰ GET کل + ۲۰۰ در هر Endpoint | شمارندهٔ دو‌سطحی؛ عبور → `GET_BUDGET_EXHAUSTED` |
| ۳ | فاصلهٔ ≥ ۱۵۰۰ms (پایان پاسخ تا آغاز بعدی) | `Bun.sleep` در `gate()` |
| ۴ | صفر payload در لاگ — فقط متادیتا | ثبت انحصاری: status · latencyMs · نام کلیدها · shapeHash · rowCount · total/totalPages · یک تاریخ «قدیمی‌ترین contractDate» (مصوب §۱۵-ب گام ۲) |
| ۵ | توکن فقط در حافظهٔ فرآیند | صفر نوشتن توکن در لاگ/دیسک؛ پاک‌سازی در `finally` |
| ۶ | Endpoint فقط از رجیستری `MELK_ENDPOINTS` | ایمپورت مستقیم از `src/lib/melk-api/endpoints.ts` — صفر hardcode مسیر |
| ۷ | هدر عین مسیر عادی داشبورد | همان‌سازی با `armCall` در `client.ts`: `Accept: application/json` + `Authorization: Bearer` + `Content-Type` فقط برای POST |
| ۸ | Timeout شبکه ۳۰s | `AbortController` — عبور → abort فوری |
| ۹ | ۴۲۹ مبدأ → توقف فوری | ثبت `Retry-After` + `RATE_LIMITED_429` |
| ۱۰ | 5xx دو بار **پیاپی** → توقف | شمارندهٔ `consecutive5xx` (یک 5xx تنها ثبت می‌شود و ادامه) |
| ۱۱ | توقف فوری دستی | `touch ABORT` در ریشهٔ پروژه → مرگ در مرز درخواست بعدی |
| ۱۲ | Teardown همیشه اجرا شود | `finally`: logout + خلاصهٔ نهایی — حتی هنگام abort |
| ۱۳ | صفر retry خودکار | صفر فشار مازاد؛ هر شکست = ثبت + تصمیم گارد |

### آشتی‌سازی صادقانهٔ POST (انحراف مستند از «هرگز POST»)

قاعدهٔ §۱۵-ا-۳ «هرگز POST» ناظر بر **مسیر داده** است (هرگز نوشتن/تغییر در مبدأ). سه فراخوانی احراز هویت ذاتاً POST هستند و در طرح مصوب §۱۵-ب (گام ۳: TTL توکن) پیش‌بینی شده‌اند:

| فراخوانی | متد | توجیه |
|---|---|---|
| `authentication/otp/login` | POST | ورود مالک (قاعده ۱۰) — ۱ بار |
| `authentication/refresh-token` | POST | آزمون TTL توکن (گام ۳ §۱۵-ب) — حداکثر ۱ بار |
| `authentication/logout` | POST | بستن نشست در teardown — ۱ بار |

**همهٔ گام‌های داده صددرصد GET.** هیچ POST دیگری در هیچ حالتی مجاز نیست.

## ۲. فاز A — درخواست OTP (۱ GET → ۱ پیامک به موبایل ثبت‌شدهٔ مالک در ARM)

```
bun scripts/recon-night1.ts --request-otp <کد پرسنلی مالک در ARM> [--force-window]
```

- Endpoint از رجیستری: `GET authentication/otp/{personnelCode}` — **کد پرسنلی**، نه شماره موبایل؛ پیامک به موبایلِ ثبت‌شدهٔ مالک در خود ARM می‌رود
- خروجی لاگ: فقط `{status, latencyMs}` — صفر محتوا
- معیار abort: status ≠ 2xx → توقف؛ پیامک نرسید تا ۱۵ دقیقه → پنجره به شب بعد موکول می‌شود (بدون فشار)

## ۳. فاز B — اجرای ۹ گام (پس از read-back کد توسط مالک)

```
bun scripts/recon-night1.ts --run <کد پرسنلی> <کد پیامک> [--force-window]
```

توکن فقط در حافظه؛ هر گام زیر با نگاشت به کلید واقعی رجیستری `MELK_ENDPOINTS.arm`:

| گام §۱۵-ب | کلید رجیستری | کوئری | خروجی مورد انتظار |
|---|---|---|---|
| ورود | `verifyOtp` (POST) | `{code, otpCode}` | ثبت زمان login + کلیدهای envelope + کلیدهای expires-مانند + نام هدرها |
| ۱ شمارش کل | `tradedCount` + `tradedTotal` | بدون بازه / `page=1&limit=100` | total/totalPages → مبنای تخمین «چند شب» و تقسیم ۵–۷ شب |
| ۲ عمق تاریخی | `tradedTotal` | `page=1&limit=100&startDate=1375/01/01` | قدیمی‌ترین contractDate صفحهٔ ۱ (تنها مقدار داده‌ای مجاز طبق §۱۵-ب) |
| ۳ TTL توکن | (در login ثبت) + `refreshToken` (POST) در پایان | — | expires_in یا نبودِ آن + رفتار refresh |
| ۴ page size | `tradedTotal` ×۲ | بازهٔ باریک ۱۴۰۵/۰۶/۲۰–۲۷، `limit=500` سپس `1000` | پذیرش/رد هر limit (فقط ثبت رفتار) |
| ۵ صفحهٔ عمیق | `tradedTotal` ×۲ | `page=50` و `page=100` با `limit=100` | زمان پاسخ + rowCount (خالی = پاسخ معتبر) |
| ۶ صفحات سبک | `tradedTotal` ×۱۰ | `page=1&limit=100` | P50/P95 دستی ده درخواست |
| ۷ بازرسی هدر | `armPublic.enums` + `tradedCount` | — | Server/Via/X-Cache/CSP/RateLimit* (عمومی + احراز‌شده) |
| ۸ فرمت آگهی | `propertiesList` | `page=1&limit=5` | نام فیلدهای قیمت/متراژ/واحد → تطبیق کاندیدهای rawPrice/rawPriceUnit/rawArea در stub آگهی |
| ۸-ب نمونه‌برداری شکل (افزوده) | `realtorsList` · `requestsList` · `visitsList` · `tradeOverviewsList` · `realtorInteractions` | هرکدام `page=1&limit=5` | کلیدهای سطح ۱ + rowCount → تبدیل ⏳های §۱۱ به ✅ |
| ۹ پایان | `logout` (POST) در `finally` | — | بستن نشست + خلاصهٔ نهایی |

**افزودهٔ ۸-ب (انحراف مستند از §۱۵-ب):** پنج GET نمونه‌برداریِ شکل پاسخ — هدف: پاسخ به ⏳های «الگوی per-endpoint» §۱۱ که ران‌بوک اصلی را به پوشش ≥۸۰٪ سؤالات D.۱ می‌رساند. هزینه: ۵ GET (مجموع کل ≈ ۲۱ GET ≪ ۱۹۰).

**بودجهٔ درخواست‌ها:** ~۲۰ GET داده + ۱ GET فاز A = ~۲۱ GET · ۳ POST احراز هویت. سقف هرگز پس زده نمی‌شود.

## ۴. معیارهای ABORT (خودکار — بدون تصمیم لحظه‌ای)

| رخداد | واکنش |
|---|---|
| ۴۲۹ از مبدأ | توقف فوری + ثبت Retry-After |
| 5xx دو بار پیاپی | توقف |
| خطای شبکه / timeout > 30s | توقف |
| ۴۰۱ (مرگ توکن) | توقف — پاسخِ خودِ سؤال TTL |
| `touch ABORT` | توقف در مرز درخواست بعدی |
| ساعت تهران ≥ ۰۶:۰۰ | توقف در مرز درخواست بعدی |
| شمارندهٔ GET ≥ ۱۹۰ | توقف |

در **هر** حالت: `finally` اجرا می‌شود → logout + خلاصه + لاگ بسته می‌شود.

## ۵. لاگ ساختاریافته (JSON خطی — `recon-night1.jsonl`)

هر رکورد: `{ts, phase, step, endpoint, method, status, latencyMs, envelopeKeys[], dataKeys[], dataShapeHash, rowCount, total?, totalPages?, oldestDate?, retryAfter?, infraHeaders?, note}`

- **صفر payload · صفر توکن · صفر PII** — تنها استثناهای مقداری مصوب §۱۵-ب: `total`/`totalPages`/یک تاریخ `oldestDate` (نتایج تجمیعی، نه ردیف مشتری)
- `dataShapeHash` = sha1 ساختار درختی کلیدها (عمق ۳) — قابل مقایسه بین شب‌ها

## ۶. گزارش صبحگاهی (پس از شب اول)

1. تبدیل ⏳های `docs/ARM-PM-RECONNAISSANCE.md` به ✅ با ارجاع مستقیم به رکورد لاگ
2. نهایی‌سازی جدول تخمین §۱۴ سند Recon (= §۵ گزارش P6.5-04): latency واقعی هر endpoint → عدد قطعی «چند شب»
3. قطعی‌سازی `limit` نهایی (۱۰۰ توصیه؛ ۲۰۰ فقط تعاملات — در صورت تأیید رفتار)
4. پاسخ صریح TTL توکن (طول عمر واقعی، رفتار refresh)
5. آرشیو: `recon-night1.jsonl` + این ران‌بوک + کامیت شاهد

## ۷. نقشهٔ بازگشت (Rollback)

شب اول **صفر نوشتار به مبدأ** دارد (جز سه POST احراز هویت استاندارد). چیزی برای rollback وجود ندارد؛ بدترین حالت = نشست باز مانده که با logout بعدی یا انقضای طبیعی توکن بسته می‌شود. در صورت abort: لاگ بسته می‌شود، هیچ گام نیمه‌کاره‌ای ادامه پیدا نمی‌کند، و اجرا به شب بعد موکول می‌شود — **بدون فشار به مبدأ و بدون فشار زمانی به مالک**.
