# BUILD-DISCIPLINE — انضباط بیلد ملکا

> سند رسمی PN-015 · مرحلهٔ ۶ (رفع ریشه‌ای Chunk 404) · مصوب ملکا-شورا-ن۰۱۹-۱۴۰۵
> تاریخ: ۱۴۰۵/۰۷/۱۸ (۲۰۲۶-۱۰-07) · نگهدارنده: GLM به سفارش مالک

## ۱ — قید مطلق: خروجی بیلد هرگز از طریق `head` لوله نمی‌شود

### فاجعهٔ مبدأ (عین‌نوشتهٔ درس PN-014)

«خروجی بیلد هرگز از طریق head لوله نمی‌شود (SIGPIPE می‌تواند بیلد را نیمه‌کاره بکشد و
سرور با نمای ناقص بالا بیاید — عیب‌یابی زنده: **chunk 404 با فایل موجود روی دیسک**؛
ری‌استارت تمیز رفع کرد). از این پس tail/tee.»

### شکل صحیح

```bash
# ✅ درست — خروجی به فایل؛ tail فقط «بعد از پایان» می‌خواند
bun run build > /tmp/build.log 2>&1; echo "EXIT=$?"; tail -20 /tmp/build.log

# ✅ درست — tee (هم‌زمان اما بی‌پایپ‌شکن)
bun run build 2>&1 | tee /tmp/build.log

# ❌ ممنوع — head با بستن لوله، SIGPIPE می‌فرستد
bun run build 2>&1 | head -5
```

**چرا؟** وقتی مصرف‌کنندهٔ لوله (head) زودتر می‌بندد، نویسنده (bundler) سیگنال SIGPIPE
می‌گیرد؛ اگر این وسط بیلد باشد، فایل‌های chunk نیمه‌نوشته یا غایب می‌مانند. سرور سپس
HTML مانیفستِ کامل را سرو می‌کند ولی فایل chunk روی دیسک نیست → **404 در مرورگر**.

## ۲ — گارد یکپارچگی chunk (K1) — معاینهٔ پیش از هر بوت

```bash
bash scripts/audit-chunk-integrity.sh --witness download/pn015/chunk-audit.json
```

سه منبع را بررسی می‌کند:
1. هر ارجاع `/_next/static/...` در HTMLهای پیش‌رندر (گویش مطلق)
2. هر ارجاع `"static/..."` در مانیفست‌های JSON بیلد (گویش نسبی)
3. پیوستگی هویت: `BUILD_ID` در برابر `fingerprint.json`

**محل‌های نصب:**
- **CI** (`scripts/ci.sh` گام ۷-ب): بیلد تازه باید بدون chunk مفقود باشد
- **پیش-بوت** (`scripts/prod-watchdog.sh`): پیش از هر اسپاون سرور؛ اگر ناقص →
  بیلد مجدد (خروجی به لاگ — قید §۱) → وارسی دوباره → اگر باز هم ناقص: هشدار در لاگ

**رفتار هدف:** سرور هرگز با بیلد ناقص بالا نمی‌آید؛ chunk 404 ساختاری حذف شده است.

## ۳ — توالی استاندارد ری‌استارت تمیز

1. `bun run build` (با قید §۱)
2. `bash scripts/audit-chunk-integrity.sh` — باید PASS بدهد
3. توقف سرور (`kill <pid>`) — نگهبان تا ۵ ثانیه بعد دوباره بالا می‌آورد (با گارد §۲)
4. وارسی مهر: `curl -s localhost:3000/api/version` → `gitSha` باید = `git rev-parse --short HEAD`
5. وارسی دامنه: `bash scripts/verify-preview-version.sh` → MATCH

## ۴ — قید ویرایش اسکریپت‌های در حال اجرا (درس زندهٔ همین شب)

اسکریپتِ bash در حال اجرا را **هرگز درجا ویرایش نکنید** — bash اسکریپت را تدریجی
می‌خواند و ویرایش، آفست خواندن را خراب می‌کند (تجربهٔ زندهٔ PN-015 روی
prod-watchdog.sh: ویرایش + ری‌استارت فوری نگهبان لازم شد). الگوی امن:
**اول توقف، بعد ویرایش، بعد بوت** — یا جایگزینی اتمیک با `mv`.

## ۵ — قید خواندن سورس با متن راست‌به‌چپ (درس زندهٔ همین شب)

خروجی ابزارها در پروژهٔ دوزبانه ممکن است نشانه‌های ASCII مجاور متن فارسی را در
«نمایش» جابه‌جا/حذف کند (نمونهٔ زنده: `[hookPath` در نمایش به `ookPath` تبدیل شد و
شبیه خرابی سورس بود). **پیش از اعلام خرابی سورس، همیشه با بایت خام تأیید کنید**:
`python3 -c "print(open('فایل','rb').read().split(b'\n')[N].hex())"` — «ترمیم» بدون
تأیید بایت، کد سالم را خراب می‌کند.

## ۶ — پس از هر بازنشانی پلتفرم

`scripts/recovery/reset-guard.sh` (K3) درخت را با شاخهٔ `main` آینه داوری می‌کند؛

## درس PN-016 (۲۰۲۶-۱۰-۰۷ ۲۳:۴۰Z) — بمب زمانی ENOSPC در بیلد

**حادثهٔ زنده:** دو بیلد پیاپی با `ENOSPC: no space left on device` روی
`mkdir .next/standalone/deliver-store/...` شکست خورد — دیسک ۹.۹GB صددرصد پر شد.

**ریشهٔ سه‌لایه (صادقانه):**
۱) `outputFileTracingExcludes` در next.config عملاً برای مسیرهای داغ
   (deliver-route) اعمال نشد — backups/db/deliver-store همگی توسط tracing
   کپی شدند (۲.۱GB + ۱.۱GB + ۲۷۶MB). پاک‌ساز واقعی همیشه `rm -rf` انتهای
   package.json/build بود («excludes/پاک‌سازی» — هر دو لازم‌اند).
۲) آن rm در **پایان** زنجیرهٔ بیلد اجرا می‌شود → اوج مصرف دیسکِ حین build =
   standalone قدیمی + کپیِ tracing تازه (تا ~۳.۵GB اضافی).
۳) رشد طبیعی deliver-store (هر جلسه ~۴۳۰MB) آستانهٔ دیسک را جابه‌جا کرد —
   حادثهٔ «پیک دیسکِ بیلد» هم‌خانوادهٔ بدهی D1 (پیک RAM).

**قاعدهٔ تازه (الزام):**
- **پیش از هر بیلد کامل:** اگر `df` فضای آزاد < (اندازهٔ deliver-store + backups + db + ۱GB) باشد →
  نخست `rm -rf .next/standalone` (کپی کهنه) و هرس بکاپ‌های قدیمی.
- **پس از هر ENOSPC:** هرگز بدون پاک‌سازی دوباره تلاش نکن — کپی نیمه‌کارهٔ
  standalone جدید خودش تا ۳.۵GB اشغال می‌کند (این‌جا دومین شکست همین بود).
- گزارش گارد size-guard هر ساعت بر دیسک <۱۵٪ هشدار می‌دهد — جدی بگیر.

**شواهد ترمیم زنده:** پاک‌سازی standalone کهنه (۳.۵GB) + هرس دو بکاپ قدیمی
(۰.۸GB) → بیلد موفق ۳۶.۷s با ۳.۷GB فضای باقی‌مانده · standalone نهایی تمیز ۱۷۹MB ·
لینک‌های /deliver پس از ری‌استارت ۸/۸ = ۲۰۰.

## درس چهارم (PN-017 · ۱۴۰۵/۰۷/۱۹): ترفند «پارکِ deliver-store» — بیلد لاغر بدون کپی شبکه‌ای

**صحنه:** بیلد نهایی روی کامیت تحویل (b24ba0b) با ENOSPC سوم شکست — رشد
deliver-store تا ~۲٫۵GB (قطعات بقا) + download/backups/db، در حالی که rm پاک‌ساز
پایانِ زنجیره است و اوجِ حین tracing به ~۴٫۷GB می‌رسد (فضای آزاد: ۳٫۸GB).

**راه‌حل (لحظه‌ای، بدون جابه‌جایی داده و بدون کپی ابری):**
```bash
mv /home/z/my-project/deliver-store /home/z/deliver-store-park   # بیرون از ریشهٔ tracing
rm -f .next/lock && bun run build                                 # tracing دیگر آن را نمی‌بیند
mv /home/z/deliver-store-park /home/z/my-project/deliver-store    # بازگشت آنی
```
- `mv` درون همان فایل‌سیستم = آنی؛ پارک بیرون از ریشهٔ repo یعنی file-tracing
  اصلاً وارد آن نمی‌شود → standalone لاغر (۱۷۹MB) بدون قفل حذفِ پسینی.
- پنجرهٔ ~۶۰ ثانیه‌ای که /deliver 404 می‌دهد، همزمان با ری‌استارت سرور است —
  هیچ سرویس زنده‌ای متوقف نمی‌شود.
- پس از بازگشت: آزمون لینک کامل (۳۰/۳۰ = ۲۰۰) الزامی است.
- هرس مکمل: بکاپ قدیمی‌ترین (نگهداری ≥۲) پیش از بیلد.

**قاعدهٔ دائمی:** هرگاه بیلد ENOSPC داد و (فضای آزاد + پارک deliver-store) کافی
است → پارک، بیلد، بازگشت، آزمون لینک. تنها وقتی دیسک واقعاً پر است به هرس
بسته‌ها/بکاپ‌ها برو.
