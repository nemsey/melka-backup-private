## ۱. قیدهای محیطی که تصمیم را شکل می‌دهند (و غیرقابل مذاکره‌اند)

تصمیم باید با سازوکار واقعی پلتفرم Z.AI سازگار باشد، نه با فرض‌های عمومی CI/CD:

1. **خط لولهٔ انتشار پلتفرم = فراخوانی ابزار Complete است.** پلتفرم پس از Complete، اسکریپت `.zscripts/build.sh` را روی همین ریپو اجرا می‌کند (`bun install` + `bun run build` + بسته‌بندی standalone) و روی Alibaba FC مستقر می‌کند. یعنی «کامیت به main ⇒ build+deploy» در این پلتفرم معادل است با: **کامیت ⇒ فراخوانی Complete** — و این معادل، قابل خودکارسازی کامل از سمت GLM است (Complete در اختیار GLM است).
2. `.git` هم در کانتینر زنده هست، هم در آرشیو `repo.tar` (۴۱۵۵ فایل)، و build.sh داخل همین کانتینر اجرا می‌شود ⇒ **git sha در زمان build قابل استخراج است.**
3. بستهٔ استقرار FC شامل `.git` نمی‌شود ⇒ git sha باید **در زمان build داخل خروجی پخته شود** (نه خواندن زنده از git در runtime استقرار).
4. ثبت/تازه‌سازی نام دامنهٔ publish فقط از مودال UI مالک انجام می‌شود (خارج از دسترس GLM) ⇒ راه‌حل باید **مستقل از نام دامنه** باشد: هر URL عمومی را بتوان با یک دستور راستی‌آزمایی کرد.
5. لینک preview از داخل کانتینر قابل کشف نیست ⇒ راستی‌آزمایی GLM باید روی **شواهد درون‌زا** (build محلی + endpoint + meta tag) بنا شود و شاهد نهایی روی لینک رسمی به مالک داده شود — با پروتکل یک‌دست.

## ۲. ارزیابی گزینه‌های پیشنهادی شورا در این محیط

| گزینهٔ شورا | در این پلتفرم | تصمیم |
|---|---|---|
| کامیت به main ⇒ pipeline اجباری (pre-commit hook یا CI) | pipeline = Complete؛ hook کامیت فایده‌ای برای انتشار ندارد | ✅ به‌صورت **پروتکل پایانِ جلسهٔ الزامی** (AGENTS.md) — بدون hook مصنوعی |
| BUILD_ID خودکار از `git rev-parse --short HEAD` + timestamp | شدنی و در همهٔ مسیرهای build پایدار (کانتینر/repo.tar) | ✅ **پذیرفته — قلب راه‌حل** |
| SW با skipWaiting + نسخه‌بندی کش با BUILD_ID | skipWaiting/claim/پاکسازی از قبل هست؛ فقط نسخه‌بندی کش با BUILD_ID می‌ماند | ✅ تکمیل می‌شود (دفاع-در-عمق) |
| یکسان‌سازی preview = همان build تولیدی، نه dev server | preview به کانتینر زنده اشاره می‌کند و این رفتار پلتفرم است؛ تغییر آن خارج از اختیار GLM | ⚪ خارج از دامنه — جبران می‌شود با شاهد نسخهٔ یکسان در هر دو مسیر (`/api/version` + meta tag در هر دو یکی است چون هر دو از همان کد build می‌شوند) |
| هدرهای no-store برای HTML + immutable برای assetها | HTML از قبل no-store است؛ assetها پیش‌فرض immutable هش‌دار | ✅ تأیید و تکمیل (افزودن `/api/version`) |
| endpoint `/api/version` + ساخت لینک از آن | دقیقاً شدنی | ✅ **پذیرفته — شاهد زندهٔ اصلی** |

## ۳. راه‌حل دائمی انتخاب‌شده (نه وصله)

**معمارهٔ «شاهد زندهٔ نسخه» (Live Build Witness) — شش مؤلفه:**

### ۳-۱. BUILD_ID خودکار و قابل‌ردیابی (کامیت-محور)
`next.config.ts`:
- `generateBuildId: () => "<gitSha8>-<yyyymmdd>-<hhmm>"` — مثال: `459939e-20260924-0712`
- استخراج sha با `execSync("git rev-parse --short HEAD")` در زمان build (با fallback صادقانه `nogit`)
- همان مقدار + `builtAt` + `gitSha` از طریق `env` در NEXT_PUBLIC_BUILD_ID / NEXT_PUBLIC_GIT_SHA / NEXT_PUBLIC_BUILT_AT **در bundle پخته می‌شود** (هم سمت سرور، هم سمت کلاینت)
- نتیجه: هر build به کامیت خودش و زمان خودش گره می‌خورد — **صفر اقدام دستی، صفر فراموشی**

### ۳-۲. Endpoint شاهد — `GET /api/version`
- خروجی: `{ buildId, builtAt, gitSha, env, runtime, source }` — **بدون احراز هویت**، `Cache-Control: no-store`
- در production: مقادیر پخته‌شده در build
- در dev: fallback زنده (sha لحظه‌ای git + زمان بوت سرور) با برچسب صادقانهٔ `env=development` — یعنی هرگز مقدار جعلی/کهنه نمی‌دهد

### ۳-۳. شاهد در HTML بدون لاگین — متاتگ `app-build-id`
`layout.tsx` متای `<meta name="app-build-id" content="<BUILD_ID>">` را server-side رندر می‌کند ⇒ `curl -s <لینک> | grep app-build-id` بدون احراز هویت نسخه را لو می‌دهد. (تست‌های موجود نشان می‌دهند ریشهٔ HTML برای کاربر لاگین‌نشده هم رندر می‌شود.)

### ۳-۴. نمایش در UI — فوتر داشبورد
فوتر `DashboardHome` (به‌جای «نسخه ۱٫۷٫۰» هاردکد): نسخهٔ زنده را از `/api/version` می‌خواند و نمایش می‌دهد: «نسخهٔ زنده: `<buildId>` — `<builtAt شمسی>` (`production/dev`)». مالک با یک نگاه می‌فهمد کدام نسخه را می‌بیند؛ همین المان، «تغییر کوچک قابل‌رؤیت» چرخه‌های راستی‌آزمایی BLOCK C هم هست.

### ۳-۵. ثبت در DB — جدول `AppMeta`
اسکیمای افزودنی (قانون حرمت داده — صفر تغییر مخرب):
```prisma
model AppMeta { id /*singleton*/ , buildId, builtAt, gitSha, env, recordedAt }
```
`instrumentation.ts` در هر بوت سرور، رکورد singleton را upsert می‌کند ⇒ DB همیشه می‌گوید «آخرین بیلدی که این سرور با آن بالا آمد چه بود» (الزام عین متن شورا: `app_meta.buildId + builtAt`).

### ۳-۶. گارد تازگی — `scripts/verify-deploy-freshness.sh`
- هر URL عمومی (preview یا publish) را می‌گیرد، `/api/version` و متاتگ HTML را می‌خواند، gitSha را با `git rev-parse --short HEAD` محلی مقایسه می‌کند
- ناهم‌خوانی/ناموفق‌بودن endpoint/نبودِ endpoint (استقرار قدیمی!) = **fail با پیام فارسی شفاف**
- در پروتکل پایان جلسه (AGENTS.md) الزامی می‌شود + خروجی آن در worklog ثبت می‌شود

### ۳-۷. خودکارسازی انتشار (معادل pipeline در این پلتفرم)
**پروتکل پایانِ جلسه — بندهای الزامی AGENTS.md (تازه‌ای):**
1. تمام تغییرات کامیت شوند
2. `bun run build` سبز + BUILD_ID جدید ثبت شود
3. `verify-deploy-freshness.sh` روی هر لینک عمومی در دسترس اجرا شود
4. **Complete فراخوانده شود** (همان دکمهٔ publish پلتفرم) — بدون این، snapshot عمومی کهنه می‌ماند
5. ثبت `published_build_id` در worklog
قانون طلایی (عین متن شورا): **«هیچ پرونده‌ای بسته نمی‌شود مگر BUILD_ID لینک publish با git HEAD یکی باشد.»**

### ۳-۸. Service Worker — نسخه‌بندی کش با BUILD_ID
`sw.js`: نام کش از `melk-dash-v6` هاردکد به `melk-dash-v7-<buildId>` (خوانده‌شده از `/api/version` هنگام install، با fallback) تغییر می‌کند؛ activate کش‌های ناهم‌خوان را پاک می‌کند. رفتار network-first برای HTML دست‌نخورده می‌ماند (هیچ ریسک رگرسیون صفحهٔ سفید).

## ۵. مرزهای صادقانه (Blocker → Alternative → Decision)

1. **Blocker**: ثبت/تغییر نام دامنهٔ publish فقط از UI مالک است (و دامنهٔ فعلی 410 است).
   **Alternative**: گارد تازگی مستقل از دامنه + شاهد روی `/api/version` هر لینکی که مالک بدهد.
   **Decision**: پس از پیاده‌سازی، Complete فراخوانده می‌شود (انتشار build جدید آماده می‌شود)؛ مالک در مودال Publish نام دامنه را ثبت/تمدید می‌کند و صحت آن را با `verify-deploy-freshness.sh` یا صرفاً دیدن فوتر می‌سنجد.
2. **Blocker**: لینک preview از داخل کانتینر قابل curl نیست.
   **Alternative**: راستی‌آزمایی سه‌بارهٔ BLOCK C روی build واقعی standalone (همان چیزی که FC سرو می‌کند) در پورت محلی + شاهد meta/API یکسان.
   **Decision**: چرخه‌ها روی standalone اجرا و مستند می‌شوند؛ شاهد نهایی برای مالک روی لینک رسمی با فوتر/متاتگ ارائه می‌شود.
3. **Blocker**: GLM کنترلی روی زمان‌بندی داخلی صف انتشار FC ندارد (سابقهٔ مورد ۲: صف پلتفرم).
   **Alternative**: گارد تازگی به‌گونه‌ای طراحی شده که در هر لحظهٔ بعدی قابل اجراست و کهنگی را قطعی تشخیص می‌دهد.
   **Decision**: گارد در پایان جلسه اجرا می‌شود؛ اگر صف پلتفرم هنوز نسخهٔ جدید را سرو نکرده بود، این وضعیت **صادقانه** گزارش می‌شود (نه ادعای انتشار) و ردیابی با اجرای مجدد گارد توسط هر جلسهٔ بعدی ادامه می‌یابد.
